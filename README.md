# 기여도 워크벤치

GitHub·Confluence 원본을 수집하고 OpenCode로 평가 초안을 만든 뒤 관리자가 근거를 확인·교정·확정하는 사내 웹 애플리케이션이다. **저장소 평가**에서 시스템·기술 스택·핵심 기능·난도·참여자를, **팀원 기여도**에서 참여 저장소와 대표 활동을 확인한다. 커밋·파일·인용과 교정 이력은 별도 근거 화면으로 분리한다. 화면과 전체 저장소 분석 방식은 [대시보드 v0.6](dashboard-redesign-v0.6.md), 기여 평가 방법은 [기능·시스템 영향 평가](management-evaluation-v0.5.md)를 참고한다.

## 실행

Node.js 22.16 이상, Git, PostgreSQL 17, npm이 필요하다. Docker는 PostgreSQL 또는 전체 배포에 선택할 수 있다. 실행·검증에 사용하는 OpenCode와 SDK는 npm lock에서 **1.19.4**로 함께 고정한다. 별도 OpenCode 실행 파일은 `CONTRIB_OPENCODE_BIN`으로 지정하며 현재 adapter는 1.x를 검증한다. native 2.x를 같은 SDK로 호출하지 않는다.

```bash
bash scripts/setup.sh
docker compose up -d postgres
# config/connections.local.json에 토큰·provider·초기 모델·관리자 계정을 설정 (URL은 로그인 후 UI에서도 수정 가능)
export PATH="$PWD/runtime/node/bin:$PATH" # setup이 로컬 Node를 설치한 경우
npm run migrate
npm start
```

다른 터미널에서 같은 Node 환경으로 `npm run worker`를 실행한다. 대시보드는 **http://127.0.0.1:3100**이다. 로그인 계정은 로컬 연결 파일의 `application.admin_username`과 `application.admin_password`에 있다. 초기 생성 암호는 무작위이며 stdout·로그에 출력하지 않는다. `HOST`, `PORT`, TLS 프록시 뒤에서는 `COOKIE_SECURE=true`를 설정할 수 있다.

## 설정과 사내 이식

`config/connections.local.json` 한 파일에서 시스템 기본 URL·토큰·DB·관리자 인증을 관리한다. 실제 파일은 Git·Docker build에서 제외하고 파일 권한 600으로 둔다. [빈 연결 템플릿](config/connections.example.json)과 [필드 설명](config/README.md)을 참고한다. `CONTRIB_CONNECTIONS_FILE`은 다른 설정 파일의 경로를 지정한다. `DATABASE_URL`은 Docker 내부 DB 경로 등 실행 환경의 DB 접속만 재정의한다.

대시보드 **설정 · 모델**에서 시스템 URL을 수정하고, **팀 · 기간 / 저장소 / Confluence 루트 / 평가 기준** 탭의 입력 폼으로 팀원·계정·공동 담당·평가 기간·루트와 저장소 연결·항목 비중을 편집한다. 항목별 추가·삭제를 지원하며 JSON을 직접 편집할 필요가 없다. 설정 저장은 새 수집부터 적용하고, 이전 설정값으로 되돌려도 현재 적용할 설정이 올바르게 선택된다. 기존 수집·평가의 설정 본문은 보존한다. [설정 예시](design/team-config.example.json)는 저장 구조를 설명한다. GitHub 시스템 URL과 레포 URL의 호스트가 일치해야 하며 private repo의 API/Git 인증은 연결 파일의 GitHub 토큰에서 가져온다. Git clone 대상에는 토큰을 넣지 않는다.

Confluence Data Center는 `deployment: data_center`와 bearer PAT, Cloud는 `deployment: cloud`와 설치에 맞는 basic/email+API token 또는 bearer 인증을 설정한다. URL에 `/wiki` 같은 context path를 포함한다. `transport: rest`가 기본이며 원본·하위·버전·댓글 수집은 결정적 코드로 수행한다. MCP는 `transport: mcp`와 도구 binding을 설정해 같은 수집 계약을 사용한다. 구체적인 설정과 검증 한계는 [연결 안내](config/README.md)에 기록한다. 자체 OAuth·SSO 인증 상태는 임의로 복사하지 않는다.

OpenCode는 기본적으로 평가용 로컬 인스턴스를 관리하며 프로세스 간 충돌을 피하기 위해 사용 가능한 로컬 포트를 할당한다. 회사의 기존 headless 서버를 쓰려면 `systems.opencode.manage_process: false`, `server_url`, `server_auth`를 설정한다. 공유 서버의 도구 권한·사내 provider·보조 모델은 운영자가 동일한 평가 전용 정책으로 구성한다. `transport: cli` 호환 경로도 있지만 이번 실제 전체 평가는 SDK로 검증했다. CLI 전체 흐름과 native OpenCode 2.x는 검증 범위 밖이다. 평가 요청에서 선택 모델을 명시하며 실패해도 다른 모델로 자동 전환하지 않는다.

OpenAI 실제 시험은 `provider_id: openai`, `protocol: responses`, `url: https://api.openai.com/v1`을 사용한다. 사내 Chat Completions 호환 LLM은 `provider_id`를 사내 ID로 바꾸고 `protocol: chat_completions`, 사내 endpoint·모델·토큰을 지정한다. `llm.models`와 `default_model_id`에서 허용 목록·기본값을 관리하며 UI에서 실행별 선택한다. 외부 LLM로 자동 대체하지 않는다. 회사 CA·프록시는 `NODE_EXTRA_CA_CERTS`, `HTTPS_PROXY`, `HTTP_PROXY`, `NO_PROXY`와 Git의 사내 CA 설정을 실행 계정에 적용한다. TLS 검증을 끄지 않는다.

모델은 **설정 · 모델 → 모델 선택 → OpenCode 연결 · 모델 불러오기**에서 실제 OpenCode SDK의 `/provider` 목록을 조회한다. 연결된 공급자의 텍스트·도구 호출 모델을 가져오며, 폐기된 모델과 연결되지 않은 공급자는 제외한다. 관리형 실행은 설정된 사내 공급자로 범위를 제한한다. 목록 조회는 LLM을 호출하지 않는다. **기본 모델로 저장**은 로컬 연결 파일에 반영하며 **수집 현황 → 평가 실행 → 평가 모델**에서 실행별로 다른 모델도 선택한다. **실제 호출 확인**은 선택 모델의 구조화 응답을 시험하고 사용량이 발생한다. 목록에 있다는 사실만으로 잔액·모델별 권한·구조화 응답 성공까지 보장하지는 않는다.

선택 모델·endpoint·프로토콜·구조화 출력 설정·문맥 한도는 실행에 고정한다. 기본 모델을 바꿔도 이전 실행은 바뀌지 않는다. 교정·재개는 원 모델을 유지하며 설정이 달라지거나 비활성화됐으면 중단한다. 다른 모델을 비교하려면 같은 원본 스냅샷으로 새 평가를 시작한다. 관리형 실행은 한 공급자의 여러 모델을, 기존 OpenCode 서버 연결은 연결된 여러 공급자의 모델을 지원한다. 동명 모델은 `provider_id/model_id`로 구분한다. 공급자 인증·도구 정책은 기존 서버에서 관리한다.

전체 컨테이너 실행은 `docker compose --profile app up --build -d`다. 최초 schema는 web/worker 시작 시 적용하며 명시적 `npm run migrate`도 제공한다. UI에서 설정을 저장할 수 있도록 web의 `config` 디렉터리는 쓰기 가능한 mount이며 worker는 읽기 전용 mount다. 원본·Git·OpenCode 작업 상태는 `runtime/`, DB는 별도 영속 volume을 사용한다. `POSTGRES_PASSWORD`와 연결 파일의 DB 암호를 일치시킨다. 기존 사내 MCP 실행 파일·인증이 호스트에 있으면 host-native web/worker가 우선이다.

회사로 소스만 가져갈 때는 `npm run package:source`로 `runtime/release/`의 압축 파일과 SHA-256을 만든다. 실제 연결 파일·토큰·DB·원본·node_modules는 포함하지 않으며 파일별 해시 manifest를 넣는다. 이 파일은 현재 평가 결과의 백업과 구분한다. 회사에서 Node 22 환경의 `npm ci`, `scripts/init.ts`, URL·토큰·모델 설정, DB migration, web·worker 실행을 진행한다. 승인된 사내 npm registry·CA를 실행 환경에 설정할 수 있다.

## 검증과 공개 자료 demo

```bash
npm test                 # 분리된 임시 PostgreSQL DB를 만들고 삭제; 외부 LLM 호출 없음
npx playwright install chromium
npm run test:browser     # 실행 중인 로컬 web을 브라우저에서 확인
npm run demo             # 실제 GitHub 원본·가상 팀원 10명·OpenCode/OpenAI 실평가
npm run verify           # Git·원본·처리 ID·인용·계정·합계를 독립 대조
npm run demo:management  # demo의 같은 원본으로 현재 기능 평가 기준의 새 실행 생성
npm run verify:management # 기능 분류·전체 원문 전달·역할·점수·과거 결과 불변 대조
npm run verify:management-browser # 완료한 실제 10명 기능 화면·원문 이동·모바일 확인
npm run verify:release   # 소스 압축 해제→새 설치→빌드→격리된 사내 호환 계약 시험
npm run doctor           # DB·OpenCode 버전·비밀을 제외한 설정 확인; 외부 모델 호출 없음
# npm run doctor -- --live  # 실제 GitHub·Confluence·선택 모델 연결 시험
# npm run resume            # API 복구 후 기존 실패 평가를 재개; 완료 판정 보존
```

demo는 Click·HTTPX 공개 Git 저장소와 2025-01-01 이상 2025-04-01 미만 기간을 사용한다. Git mirror가 없으면 먼저 수집기가 내려받으며 demo 초기 준비 경로는 `runtime/repos/click.git`, `runtime/repos/httpx.git`다. 실제 작성자 이메일 중 10개를 가상 팀원에 명시적으로 연결한다. 사람 이름을 추측해 계정을 합치지 않는다. `config/team.local.json`은 재현용 범위를 저장한다.

자동 시험용 PostgreSQL 계정에는 임시 DB 생성·삭제 권한이 필요하다. `npm test`와 격리 브라우저 시험은 별도 DB와 로컬 계약 LLM을 사용하고 종료 시 삭제한다. 공개 자료 실평가 DB에 계약용 점수를 넣지 않는다. `npm run verify`는 공개 자료 평가가 끝나지 않았으면 의도적으로 실패 종료한다.

`npm run verify:process`는 현재 선택한 실제 모델로 바이너리 내용 미관찰·빈 줄 변경·활동 수 감도 표본을 시험하며 API 사용량이 발생한다. 합성 활동 수는 격리된 감도 입력에만 넣고 원본·실평가 판정은 바꾸지 않는다. 동일 결과를 한 번 관찰했다고 일반적인 편향 부재를 보장하지 않는다. 표본에서 확인한 의미상 오류와 한계는 [품질 검토](evaluation-quality-review.md)에 남긴다.

공개 시험은 Git 이력·docs에 범위를 고정하고 인증 없는 GitHub API의 PR·리뷰·CI 수집은 결손으로 표시한다. 실제 Confluence와 내부 토큰의 호환성은 별도 REST/MCP 계약 시험으로 확인한다. demo에서 100% 사내 연동이 검증됐다고 주장하지 않는다. 실제 회사에서는 `demo` 설정을 제거하고 Confluence 루트·GitHub API 토큰을 입력한다. 평가 결과는 DB·원본과 함께 보존하고 `runtime/verification/`의 검증 산출물과 대시보드에서 확인한다.

## 운영과 보존

수집·평가 작업은 PostgreSQL 큐에 저장된다. 실패·취소는 대시보드에서 재개하며 완료 근거·판정은 중복 반영하지 않는다. worker가 사라져 lease가 만료되면 다른 worker가 재개한다. 원본 파일·과거 AI 결과를 편집하지 않는다. 교정은 별도 이벤트로 저장하고 관련 보고 전체를 재평가한다. 같은 모델·스냅샷을 유지하며 모델 변경은 새 실행으로 남긴다.

평가 프롬프트·검증기 버전도 실행에 고정한다. 코드 업데이트로 기준이 달라지면 과거 판정을 이어 붙이지 않고 새 평가를 생성한다. 자료 평가의 원문 구간과 개인 종합의 근거 ref는 코드가 원본 ID로 확장하며, 누락·중복·알 수 없는 참조는 거부한다. 바이너리 내용 없이 변경 표시만 있으면 내용 품질은 미확인으로 제한한다. `CONTRIB_EVALUATION_PARALLELISM`은 worker의 동시 호출 수를 1~8로 제한하며 기본값은 팀 설정 또는 2다.

백업은 PostgreSQL dump와 `runtime/objects`를 같은 시점 기준으로 보존한다. `config/connections.local.json`은 별도로 접근 제한된 백업을 한다. Git mirror는 원본 객체 재확보·diff 대조에 필요하므로 소급 검증이 필요하면 함께 보존한다. 평가 모델에는 OS·파일·검색·수집 도구를 허용하지 않으며 구조화 결과 반환 도구만 사용한다. 다운로드한 레포의 코드·스크립트는 실행하지 않는다.

기본값 `evaluation_policy.artifact_mode: feature_first`에서는 코드가 개별 자료의 사실·역할·평가 단위를 색인하고, AI가 전체 원문 구간에서 실제 변경 전후의 의미를 먼저 색인하고 이를 기능 과제로 묶어 종합한다. 이 의미 색인은 커밋별 개인 평가나 점수표가 아니다. 커밋마다 AI 점수를 매기고 합산하지 않는다. 필요한 경우 `full`을 명시해 자료별 AI 해석을 추가할 수 있다. 그 결과도 개인 등급의 단순 합계로 쓰지 않는다.

기간 말에 고정한 레포 구조·등록 요구 문서·소스 인터페이스와 명시적으로 연결한 Confluence 루트가 시스템 맥락을 제공한다. 문서는 이전 버전과의 차이를 별도 원문으로 보존하며 기존 페이지 전체를 마지막 편집자의 새 성과로 취급하지 않는다. 같은 목표의 구현·테스트·문서를 하나의 개선으로 묶고, 다른 목표가 포괄적인 이름 아래 잘못 합쳐지지 않았는지 별도 AI 검토를 남긴다. 모든 원문 구간이 의미 색인 모델의 입력에 전달됐는지, 이후 기능 종합이 해당 색인과 인용·요약 계보를 빠짐없이 연결하는지 검증한다. 이는 AI가 모든 의미를 정확히 이해했다는 보장은 아니다. 기존 시스템의 전체 파일·문서는 별도의 기존 동작 계약으로 읽으며 변경 성과 목록에 합치지 않는다. 최종 기능·개인 설명은 실제 변경 사실에서만 구성하고 개인별 인용 선택지도 해당 인물의 원본으로 제한한다.

원본 계정의 작성자·공동 작성자·버전 편집자 역할은 코드가 연결한다. AI의 역할 설명은 가설이며 실제 역할 기록을 대체하지 않는다. 담당 배정은 소유권 증명이 아니고 병합 기록만으로 다른 작성자의 구현·검증을 귀속하지 않는다. 직접 리뷰·검증·내용 근거가 없는 평가 항목은 코드가 null로 제한한다. 낮은 점수는 개인 변경과 기간 말 상태에서 확인한 미해결 결함 근거가 있어야 허용하며, 근거가 있는 항목도 자동으로 3점을 부여하지 않는다.

개인 초안은 별도의 AI 사실 검사도 거치지만 이 검사 역시 오류를 놓치거나 올바른 한계 설명을 거부할 수 있다. 모든 AI 개인 초안은 **원문 대조 · 관리자 검토**에서 정확한 인용·확인한 설명·이유를 별도 기록해야 확정할 수 있다. 제한된 재시도 후 AI 검사끼리 충돌한 초안은 ‘점수 채택 보류’로 표시하며 검사 응답을 보존한다. 이런 초안은 원문 검토에 더해 관리자 등급과 이유를 별도로 입력해야 한다. 원문 인용 일치 검사는 설명의 진실성을 자동 보증하지 않는다. 실제 인사 운영에서 이 검토는 책임 있는 관리자가 수행해야 한다.

공개 demo의 검토·확정 기록은 자동화 에이전트가 기능을 검증한 **가상 인물 시스템 시험**이다. 독립적인 사람의 심사나 공개 작성자의 실제 인사평가를 뜻하지 않는다. 가장 저렴한 `gpt-5-nano` 시험에서 역할 혼동·실행 과장·점수 변동을 관찰했으므로 이 모델의 점수를 보상 산식에 바로 연결하지 않는다. 선택한 사내 모델도 별도 표본 교정과 관리자 검토가 필요하다.

현재 실제 검증 상태와 남은 항목은 [검증 리포트](verification-report.md)에 기록한다. 문서에 기재한 검증 명령의 존재를 실제 통과로 간주하지 않는다.

등록된 팀원의 역할이 없는 변경도 전체 원문 의미 색인과 근거 장부에 보존한다. 다만 개인 기여의 기능 분류에는 역할이 있는 변경만 제공하고, 나머지는 코드가 ‘다른 작성자의 변경 · 시스템 배경’으로 구분한다. 이 배경 묶음은 개인의 기능 개발 성과나 점수 대상이 아니다. 공동 기능의 개인 설명은 고정된 사람 참조와 사람별 실제 변경 사실을 사용해 다른 사람의 작업과 대조한다.

교정·기준 변경으로 재평가할 때 원문 읽기는 사람의 점수 판단과 별도로 재사용할 수 있다. 같은 원문 구간·읽기 지시·모델의 응답을 현재 필수 인용 조건으로 다시 검증하고 원래 배치 요청·schema·응답·세션을 연결한다. 배치 구성이 달라져도 원문 단위의 출처는 보존한다. 개인 역할은 현재 교정에 따라 코드가 다시 연결하고 기능 분류·평가의 변경된 입력은 새로 호출한다.

교정 화면의 ‘교정의 원문 인용’은 선택 항목이다. 보존 원문과 일치하는 8~2000자 구간을 입력하면 AI의 요약에서 선택되지 않았던 문장도 재평가 인용 선택지에 직접 포함한다. 해당 행이 고정한 기간 말 파일에도 있으면 그 상태의 인용도 코드가 함께 제공한다. 기능의 영향·역할 해석 교정은 해당 기능과 관련 개인 결과에 적용하며 기능 분류 자체를 다시 지시하지 않는다. 분류를 바꾸려면 근거 탐색의 범위를 한정하지 않은 사실·해석 교정을 사용한다.

Docker에서 실행 계정의 UID/GID가 1000이 아니면 `CONTRIB_UID`와 `CONTRIB_GID`를 해당 계정 값으로 설정한다. 읽기 전용 연결 파일의 600 권한과 runtime의 쓰기 권한을 유지하기 위한 설정이다.

병합 기록의 전체 diff도 원문 색인과 장부에서 보존한다. 다만 병합만 기록된 사례를 이유로 타인이 작성한 저장소 파일 전체를 개인 구현의 기간 말 맥락으로 확장하지 않는다. 직접 기여한 변경의 파일 맥락과 통합 역할의 관찰 한계를 구분한다. 개인 요약 생성도 설정된 동시 호출 수 안에서 처리한다.

현재 의미 색인은 한 모델 호출·새 세션에 하나의 원문 읽기 단위만 제공한다. 변경 줄을 인용할 수 있으면 그 줄의 인용을 요구하고, 개인 요약에는 본인의 변경 사실과 코드가 연결한 역할을 별도 제공한다. 공동 기능 전체를 개인 공로로 복사하지 않기 위한 입력 계약이다. v11 다중 단위 호출의 의미 혼선과 실제 검토 결과는 품질 검토 문서에 기록한다.


개인 기능 포트폴리오는 공유 기능 보고와 별도로 생성·저장한다. 코드가 실제 작성·공동 작성·편집·리뷰 역할에 연결된 원문만 개인 입력으로 선택하고, 공유 기능 전체의 제목·성과 문장을 개인 모델에 복사하지 않는다. 같은 원본의 공동 작성자는 함께 표시하되 개인 공로의 독점성을 추정하지 않는다. 병합만 남은 기록은 별도 통합 기록으로 보존하며 구현 난도·품질 판정의 근거로 사용하지 않는다.

기간 말 결함에는 그 사람의 변경이 고정한 기본 브랜치에 반영됐다는 코드의 확인과 변경·기간 말 원문 인용, 구체적인 실패 조건이 필요하다. 브랜치 작업의 위험을 운영 결함으로 바꾸거나 한 번의 수정을 본인이 도입하고 해결한 결함으로 설명하지 않는다. 이 검사는 귀속·시점의 하한이며 AI의 의미·난도·효과 해석을 인증하지 않는다. 관리자 검토·교정과 별도 최종 결정 경로를 함께 사용한다.


기간 말 파일의 인용 구간은 `context_only`·`at_period_end` 중 하나라도 있으면 코드가 비공로 배경으로 정규화한다. 개인 변경 난도를 생성하는 입력에는 저장소 전체 난도 숫자를 포함하지 않는다. 관리자 화면은 시스템 난도와 개인 변경의 난도를 별도로 보여 준다.


개인 기능·검토·포트폴리오의 원문 입력·교정·모델·schema·평가 지시가 같고 검증 오류를 고치라는 재시도 안내만 다른 성공 응답은 현재 검사를 다시 통과한 뒤 재사용한다. 원래 요청과 재시도 안내·응답·세션은 연결해 보존한다. 실제 사실 교정·원문·모델·응답 계약이 바뀌면 이 규칙으로 재사용하지 않는다. 무관한 팀원의 교정 때문에 같은 근거의 다른 팀원 평가를 불필요하게 다시 생성하는 일을 줄인다.
